## ADDED Requirements
### Requirement: Mutation Operation Identifiers
The collaboration pipeline SHALL assign a per-mutation `opId` generated by `generateRandomId(32)` and transmit it end-to-end.

#### Scenario: Mutation has opId
- **WHEN** a client emits a mutation in a changeset
- **THEN** the mutation includes a non-empty `opId` generated via `generateRandomId(32)`

### Requirement: Idempotent Deduplication by Client
The server SHALL deduplicate mutations using the `(clientId, opId)` pair and return the previously applied result for duplicates.

#### Scenario: Duplicate opId from same client
- **WHEN** the server receives a mutation with an `opId` that already exists for the same `clientId`
- **THEN** the server responds with the previously stored result without reapplying the mutation

### Requirement: Operation Persistence
The server SHALL persist mutation `opId` values in the operation log storage.

#### Scenario: Store opId
- **WHEN** a mutation is applied
- **THEN** the operation log entry stores the mutation `opId` and `clientId`

## MODIFIED Requirements
### Requirement: Pre-Sync Composition
The client OT pipeline SHALL compose pending mutations before sending changesets when possible and SHALL flush changesets serially per document.

#### Scenario: Compose pending mutations
- **WHEN** multiple pending mutations are compatible for composition
- **THEN** the client sends the composed mutations to reduce payload size

#### Scenario: Serial changeset flush
- **WHEN** a client has an in-flight changeset for a document
- **THEN** it queues subsequent pending mutations and waits to flush until the in-flight changeset is acknowledged
